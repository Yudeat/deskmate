deskmate — System Design

Personal desktop screen assistant — hotkey → vision → annotate/act · single user · BYOK · zero backend

What to use — v1 practices

  • • Event-driven capture: only on hotkey, never continuous
  • • Per-display 0–1000 relative coords × DIP bounds (kills mixed-DPI drift)
  • • thumbnailSize=1080: downscale for free, no resize code
  • • BYOK: config.json, 3 providers, one JSON-only prompt
  • • JSONL memory: append + tail 20 — no DB, no embeddings
  • • Fail loud: permission self-check at startup
  • • One stdlib test file for jsonfix (node:test + assert)

What NOT to do

  • • ✗ Continuous / screen-delta screenshots → rate limits, latency
  • • ✗ Vector DB / embeddings for personal memory — overkill
  • • ✗ GSAP or canvas for a bounding box — SVG + CSS fade is enough
  • • ✗ n8n / Flowise / workflow servers in v1
  • • ✗ Three execution engines — one AppleScript path
  • • ✗ Trusting raw LLM pixels — confirm before CLICK/TYPE
  • • ✗ Absolute pixel coords across monitors — always per-display fractional

Latency budget & stack

  • • Hotkey → annotation on screen: ~1.5–3s
  • • capture+encode ~150ms · vision 1–2.5s · parse+render <50ms
  • • Electron, plain Node — no bundler, ~15 files
  • • Gemini 2.5 Flash primary · Groq / Ollama fallback
  • • Phase 2 voice: say + whisper.cpp (Web Speech ≈ broken on WKWebView)
  • • OSS later: Electron = biggest contributor pool; backend files port to Tauri unchanged if ever needed
